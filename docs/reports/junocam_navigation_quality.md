## 1. Camera model and SPICE (JunoCam instrument kernel)

Source: `juno_junocam_v03.ti`, fetched from https://naif.jpl.nasa.gov/pub/naif/JUNO/kernels/ik/juno_junocam_v03.ti
(Version 0.3, **7 August 2019**, Boris Semenov/NAIF; supersedes v0.2 3-Aug-2017, v0.1 29-Sep-2016, v0.0 9-Jun-2009 — version history quoted from the kernel header). Distortion/timing values sourced in the kernel to "E-mail from Mike Caplinger, MSSS re updated Junocam camera model, 06/20/17."

- **Frame/NAIF IDs [documented]**: `JUNO_JUNOCAM` (-61500, total FOV), `JUNO_JUNOCAM_BLUE` (-61501), `JUNO_JUNOCAM_GREEN` (-61502), `JUNO_JUNOCAM_RED` (-61503), `JUNO_JUNOCAM_METHANE` (-61504). Mounting alignment is defined in the separate Juno FK file (not the IK).
- **Focal length / pixel size [documented]**, identical for all 5 IDs: `FOCAL_LENGTH = 10.95637` mm, `PIXEL_SIZE = 0.0074` mm.
- **Distortion model [documented]** — a radial (Brown-type) model with iterative "undistort": given `cx=DISTORTION_X`, `cy=DISTORTION_Y`, `k1=DISTORTION_K1`, `k2=DISTORTION_K2`, `fl = FOCAL_LENGTH/PIXEL_SIZE`, radius `r2 = xd²+yd²`, distortion factor `dr = 1 + k1·r2 + k2·r2²` applied multiplicatively to (x,y) in focal-plane units, then offset by (cx,cy) to pixel coordinates. Coefficients (identical k1/k2 across all bands; only the y-offset differs per band):
  - `K1 = -5.9624209455667325e-08`, `K2 = 2.7381910042256151e-14` (all bands)
  - `DISTORTION_X = 814.21` (all bands)
  - `DISTORTION_Y`: METHANE = 315.48, BLUE = 158.48, total(-61500) = 78.48, GREEN = 3.48, RED = -151.52.
  - The full Python-style pseudocode for `distort()`/`undistort()` is given verbatim in the kernel (§"Optical Distortion").
- **Filter strip positions [documented layout, inferred exact row bounds]**: The kernel's ASCII FOV diagram shows four 128-pixel-high framelet strips stacked top-to-bottom in order **METHANE, BLUE, GREEN, RED**, each spanning the full 1648-pixel-wide line, boresight nominally at local pixel (827.0, 64.0) within each 128-row strip. Each line has "23 dark pixels at the start... followed by 1608 photoactive pixels and additional dark, isolation, and overscan/dummy pixels for a total of 1648 pixels per line" [documented, quoted]. The kernel does not itself tabulate absolute detector row ranges for each filter; the DISTORTION_Y values above are the closest documented proxy (relative vertical boresight offsets between bands) — treating them as row-center offsets is **[inferred]**, not asserted by NAIF.
- **Timing conventions [documented, quoted verbatim]**: "Each Junocam image consists of multiple frames, each a readout of a portion of the CCD containing one or more filter strips ('framelets')... The timing of each frame is set by a base time (the 'START_TIME' keyword in the PDS label...) and an interframe delay ('INTERFRAME_DELAY'). We have found that there is a fixed bias of 61.88 msec in the start time with a possible jitter of order 20 msec relative to the reported value (that is, you should add 61.88 msec to the value of START_TIME.) You should also add 1 msec to the value of INTERFRAME_DELAY." Encoded as `START_TIME_BIAS = 0.06188` s and `INTERFRAME_DELTA = 0.001` s for all 5 band IDs. No TDI parameters appear in the IK itself (TDI stage count is a per-image PDS label field, not an IK constant — see §3 and the EDR/RDR SIS in §2).
- Nominal resolution stated in the kernel's instrument description (quoting MSSS website, ref [7]): "approximately 15 kilometers (9.3 miles) per pixel" for the first seven orbits [documented].
- **Filters section of the kernel is literally "TBD; may be based on MRO/MARCI"** [documented] — the IK itself carries no filter bandpass/transmission data; that lives in Hansen et al. 2017 (see §5).

## 2. Existing open pipelines

- **USGS ISIS3** (`junocam2isis`, `spiceinit`, `cam2map`) — C++/Qt, part of the actively maintained ISIS3/ISIS package (DOI-USGS/ISIS3 on GitHub). `junocam2isis` splits one PDS product into one ISIS cube per framelet per filter [documented, https://isis.astrogeology.usgs.gov/.../junocam2isis/junocam2isis.html]. `spiceinit` attaches SPICE geometry; `cam2map` projects level-1 cubes to a map (level-2) [documented, cam2map docs]. **Known limitations [documented from GitHub issues]**: backplane lat/lon "vanish 7–8 pixels away from the image limb boundary" after spiceinit+junocam2isis, attributed to possible SPICE/body-frame mismatch or "hard-coded filter offsets in the JunoCam model" (issue #4768); reported `spiceinit` failures/"No instrument position available" errors on some JunoCam products (issue #5724); open camera-model questions (issue #4913). Runs headless/CLI on Linux (standard ISIS CLI apps) [inferred from tool design, not separately verified this run].
- **NASA Ames Stereo Pipeline (ASP)**, JunoCam example page (stereopipeline.readthedocs.io) [documented]: builds on ISIS `spiceinit` for pointing, supports CSM-based lens-distortion refinement (OpenCV radial-tangential or instrument-specific), produces DEMs/orthoimages with lat/lon via mapprojection, runs headless via CLI. Documented limitations: "systematic artifacts in the elevations" from "not well-modeled distortion and TDI effects," sparse framelet overlap causing DEM gaps, and mosaic seams.
- **ramanakumars/JunoCamProjection** (GitHub) [documented via README fetch]: Python + a Linux-amd64-only C extension, **GPL-3.0** license, ~101 commits; projects images onto a lat/lon grid; ships example Jupyter notebooks for single-image and multi-image mosaicking; README does not explicitly mention SPICE, timing-bias, or distortion handling in the fetched content — **[not found]** whether it applies the IK's START_TIME_BIAS/K1/K2.
- **kmgill/junocam_processing** (Kevin M. Gill) [documented via README fetch]: written in **Rust**, license not stated in fetched content, ~46 commits; described as an "end-to-end calibration, blemish repair, & hot pixel correction pipeline" via a `process` subcommand; requires the CSPICE toolkit and a `JUNOBASE` env var pointing at Juno SPICE kernels (so it does use SPICE); accepts camera-orientation (pitch/roll/yaw) and lens-model (cylindrical/fisheye) parameters; ships a Dockerfile, so headless Linux/cluster use is supported. Whether it outputs per-pixel lat/lon was **[not found]** in the fetched excerpt. Gill also maintains `kmgill/cassini_processing`, whose `doc/JunoCamProcessing.md` documents a workflow of SPICE-kernel initialization per framelet plus equirectangular map projection [documented, page title/URL only — content not deep-read this run].
- **BrianSwift/JunoCam** (GitHub) [documented via README fetch]: **Mathematica** notebooks, **MIT** license, ~32 commits; author states explicitly these are "not 'production quality' tools"; GUI/notebook-oriented (requires Mathematica or Wolfram CDF Player), so **not** straightforwardly headless-clusterable; no SPICE/timing/lat-lon mention found in fetched content.
- **cosmas-heiss/JunoCamRawImageProcessing** and **AstroMasztalerz/JunoProcessor** — found by search (GitHub) but **not fetched/read this run** [not found — flagged for follow-up, not evaluated].
- **Gerald Eichstädt's method**, as described secondhand by Orton et al. (2017) and Tabataba-Vakili et al. (2020) [documented via search snippets, not primary-read]: an image-processing pipeline in which "the orientation, optical properties, and observation timings are optimised via manual comparison of the observed limb positions" — i.e., a manual/iterative limb-fit refinement on top of the nominal SPICE pointing, rather than pure SPICE reprojection. One search snippet (source unverified this run) also cites a simpler independent camera model with a single radial term "K1 = 3.839251e-8" (Brown 1966 formulation) — this differs numerically from the NAIF IK's K1/K2 above and should be treated as a **separate, non-official** calibration, not cross-checked against the IK in this review.
- **Björn Jónsson**: credited (search snippets, e.g. Planetary Society profile, Mission Juno "Maps Archive") with producing global/polar Jupiter maps combining JunoCam and Cassini/JIRAM data, and with IMG2PNG format-conversion tooling; no distinct navigation/distortion methodology document was located and read in this time box **[not found]**.
- **PDS EDR/RDR SIS** — `JUNO_JNC_EDR_RDR_DPSIS.HTM` (planetarydata.jpl.nasa.gov) [documented, fetched directly]: defines EDR = "NASA Level 0" (raw voltages/counts, 8-bit samples, time-ordered) and RDR = "NASA Level 1A" (instrument-signature-corrected, scaled to units where a white Lambert surface at solar distance and commanded exposure = 10,000 DN; 16-bit samples). Framelet definition: "one to four 'framelets', each 1648 pixels wide and 128 pixels high," optionally 2×2 summed on-board. `TDI_STAGES_COUNT` is a per-image label field, integer 1–255.

## 3. Data quality over the mission

- **Nominal design life**: JunoCam was explicitly built for outreach over "Juno's first seven orbits," expected to keep operating "as long as possible in the harsh jovian radiation environment" after that [documented, quoted from the IK's Instrument Description, sourced to MSSS/Hansen et al. 2017].
- **Onset and progression of radiation damage [documented, from search summaries of Ravine et al. 2025 and JPL/Universe Today coverage]**: JunoCam operated with "little degradation" through the 34-orbit prime mission. Symptoms first appeared around **orbit/perijove 47**; by **perijove 56** (image dated 22 Nov 2023, PIA26642) "nearly all... images were corrupted," described as grainy with horizontal streaking traced to "high DC offset." Two distinct radiation-dose anomalies are named: (1) a start-up issue in a linear voltage regulator (LM137, per a ResearchGate figure caption), and (2) a CCD image-sensor performance issue.
- **Annealing recovery [documented, from search summaries]**: engineers commanded JunoCam's heater to raise camera temperature to **77 °F**, "much warmer than typical for JunoCam." One figure caption describes "Orbit 56 pixel offset decreasing with annealing heating, then dropping near zero" over **~140 hours** of annealing. At **perijove 57 (30 December 2023)**, JunoCam returned inbound, north-polar, and outbound imagery "free of the problems seen at PJ56," in time to support the **Io flyby**. Refereed source: **M. Ravine, M. Caplinger, C. Hansen, L. Vittling, D. Krysak, S. Bolton, "Recovery of JunoCam by Annealing in the Jovian Radiation Environment," IEEE Transactions on Nuclear Science** (presented IEEE NSREC, Nashville, 16 July 2025; IEEE Xplore document 11396381; ResearchGate record 400777264). Press coverage: JPL news "NASA Shares How to Save Camera 370-Million-Miles Away Near Jupiter" (jpl.nasa.gov), Universe Today "NASA's Junocam Heals Its Radiation Damage," Hackaday (23 Jul 2025), phys.org (2025-07). A related EPSC-DPS 2025 abstract (EPSC-DPS2025-1226) exists but was not read this run.
- **Timing-offset issue** — the fixed **61.88 ms START_TIME bias** and ~1 ms INTERFRAME_DELAY correction documented in §1 is a *calibration correction* published by NAIF/MSSS in the IK, not a radiation-induced anomaly; keep it distinct from the PJ56 "pixel/DC offset" radiation symptom above **[documented distinction]**.
- **Companding/decompanding [documented, quoted from the EDR/RDR SIS]**: onboard, 12-bit ADC values are compressed to 8 bits via a "SQROOT" (square-root-like) companding table; example table entries quoted from the SIS: 8-bit DN 24 → 12-bit 25; 8-bit 90 → 12-bit 255; 8-bit 255 → 12-bit 2879. Three additional linear companding modes (LIN1, LIN8, LIN16) exist. RDR production explicitly "inverts the onboard 12-to-8-bit companding" to recover linear DN before radiometric scaling. Hansen et al. 2017 (secondhand, search snippet) additionally describes this as "similar to gamma correction" and states it is lossless within the table's quantization.
- **Hansen et al. 2017** — full citation: **C.J. Hansen, M.A. Caplinger, A. Ingersoll, M.A. Ravine, E. Jensen, S. Bolton, G. Orton, "Junocam: Juno's Outreach Camera," Space Science Reviews 213, 475–506 (2017), DOI 10.1007/s11214-014-0079-x** [documented]. PDF mirror at missionjuno.swri.edu/pub/e/downloads/JunoCam_Junos_Outreach_Camera.pdf was located but not text-extracted in this run (binary PDF; WebFetch could not decode it) — filter/flat-field facts below come from search-engine snippets of this same paper, not a direct read, so are flagged **[documented via secondary snippet, not primary-verified]**.

## 4. Scientific use (winds, cyclones, spectra)

- **Orton et al. 2017**, "The first close-up images of Jupiter's polar regions: Results from the Juno mission JunoCam instrument," *Geophysical Research Letters* 44, 4599–4606, DOI 10.1002/2016GL072443 [documented]. First-perijove polar images at **50–70 km/pixel** spatial scale, low emission angle; used JunoCam's terminator view to measure haze-layer altitude above the main cloud deck.
- **Tabataba-Vakili et al. 2020**, "Long-term tracking of circumpolar cyclones on Jupiter from polar observations with JunoCam," *Icarus* 335, 113405, DOI present in ADS record 2020Icar..33513405T [documented citation]. Tracked pentagonal (south) and octagonal (north) circumpolar cyclone (CPC) arrangements **2016–2018**; found the arrangements largely stable, southern pentagon drifting westward monotonically, northern octagon more variably; measured internal cyclone tangential-wind profiles (peak then declining with radius). Navigation/method: per a search-engine summary citing the same Eichstädt pipeline as Orton 2017, "orientation, optical properties, and observation timings optimised via manual comparison of observed limb positions"; a separate snippet reported limb-fit uncertainty "better than 2° in the position of the south pole" — this specific number is **[documented via secondary snippet only, not confirmed by direct read of the paper]**, flagged for verification against the primary text/PDF (paywalled at ScienceDirect; ADS/ResearchGate fetch attempts in this run returned 403/405 errors).
- **Orton et al. 2020**, "A Survey of Small-Scale Waves and Wave-Like Phenomena in Jupiter's Atmosphere Detected by JunoCam," *JGR Planets*, DOI 10.1029/2019JE006369 — identified by title/search only [documented existence, content not read]; closest match in this literature set to a spatial-statistics/wave-survey use of JunoCam.
- **Barrado-Izagirre et al.** (e.g., A&A 2013 and a related "Changes in Jupiter's Zonal Wind Profile preceding and during the Juno mission," ScienceDirect) — a global/2D cross-correlation cloud-tracking method originally built for **ground-based amateur telescope images**, not JunoCam-specific; found by search but its Juno-mission-updated version's use of JunoCam frames specifically was **[not found/confirmed]** in this time box.
- A JunoCam-specific cloud-tracked-wind-field paper using close-spaced image *pairs* (baseline, resolution, accuracy) was **not found** in this time box; search results instead surfaced a general statement that JunoCam perijove imaging cadence ("features separated by at most an hour") is often "insufficient to detect [cloud] motion... for dynamical studies" [documented via search snippet, source article not identified/verified].
- Best-case close-approach resolution: one search snippet states perijove altitudes "as small as 3,500 km" give "pixel-to-pixel spacing as good as 3 km" — **[documented via secondary snippet, source not verified]**; contrast with the IK's own "~15 km/pixel" figure for the nominal 7-orbit mission (§1), which are consistent (much closer perijoves in the extended mission vs. the original 7-orbit design).

## 5. Photometry

- **No absolute radiometric/flat-field calibration for outreach-grade use [documented via secondary snippet of Hansen et al. 2017]**: "a flat field correction would also be done at this step, but this is not currently implemented as the instrument response is fairly uniform without it." RDR values are scaled so a white Lambert surface at solar distance with the commanded exposure time reads 10,000 DN (§2/§3, EDR/RDR SIS, directly fetched and quoted).
- **Filter bandpasses [documented existence, numbers not extracted this run]**: Hansen et al. 2017 reports filters from **Barr Associates** (Westford, MA); "filter transmissions as measured by Barr from witness samples" with center wavelengths/bandwidths tabulated in the paper (table not read in this run — PDF was undecodable via WebFetch); methane filter centered ≈890 nm [documented, appears consistently across multiple snippets/the IK's Instrument Description].
- **Recent explicit statement of the calibration gap**: **A.P. Singh, S. Shah, R. Sankar, et al., "Structure-Preserving Unpaired Image Translation to Photometrically Calibrate JunoCam with Hubble Data," arXiv:2511.22668 (27 Nov 2025)** [documented, fetched directly]. States JunoCam "lacks the absolute photometric calibration required to convert its raw sensor readings into physical units of radiance," designed for outreach rather than quantitative science. Proposes an unpaired image-to-image (Schrödinger Bridge / "SP-I2I") deep-learning method calibrating JunoCam frames against HST as a radiometric reference, with a learnable Laplacian-pyramid gate separating low-frequency color/radiance from high-frequency spatial structure. For illumination/geometry, the paper applies a **Gaussian high-pass filter** to flatten large-scale illumination/curvature in mosaics as a preprocessing step — this is *not* a physical Minnaert or Lambert phase-angle correction.
- **Minnaert/Lambert limb-darkening normalization specifically for JunoCam**: **not found** as confirmed practice in this time box. Search results returned only *general* Jupiter-imaging Minnaert-correction formalism, `(I/F)/(I/F)₀ = μ₀^k · μ^(k−1)`, associated with other datasets/PDS GLOBALMAP products (context suggests Cassini ISS / other imaging archives, not confirmed as JunoCam-specific) — flagged **[not found, do not attribute to JunoCam without primary confirmation]**.
