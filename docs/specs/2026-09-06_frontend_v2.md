No GPU on the server: all rendering happens in the browser (WebGL).

## Why v2 (from the owner's test of v1)
Colour map changes did not apply; panels did not repaint; the movie
rendered but was not shown; hover on the catalog did nothing (points
were rasterised); zoom changed the aspect ratio; "send to Poles/Strips"
was an opaque metaphor. v2 must make each of those impossible by
construction: client-side colour maps and stretch, GPU point picking
with tooltips, locked-aspect views, native `<video>`, and a visible
selection tray instead of send-to buttons.

## Stack (fixed)
Vite; React 18; TypeScript strict; `zustand` for state; `deck.gl`
(`@deck.gl/core`, `@deck.gl/layers`, `@deck.gl/react`) with
`OrthographicView` (aspect locked by construction); `apache-arrow` for
the catalog and strips tables; `plotly.js-dist-min` for curves;
plain CSS modules (no component framework). Keep the dependency list to
those plus dev tooling (vitest, @playwright/test, typescript, vite).

## Layout
A top bar (app name, mirror path and counts from `/api/config`, a
jobs indicator that opens a job list), a left column of view tabs
(Catalog, Poles, Strips), a right column that is the **Selection
tray** (always visible), and the main area for the active view.

### Selection tray (the organising object)
- Shows the current working selection: count of frames, orbits,
  latitude range, bands; a name field; "Save" (POST /api/selections),
  a list of saved selections (GET) with load and delete; "Clear".
- Any view can add to or replace the working selection: catalog lasso
  or box, catalog table row checkboxes, a saved selection, or "all
  frames matching the current filters".
- The tray offers actions that consume the selection: "Build stack…"
  (opens a dialog: region from a fixed list read from the stacks
  listing plus the four registry names, band, level; POST
  /api/stacks/build with `selection_id` after saving), and "Show in
  Strips" (filters the strips view to strips whose frames intersect
  the selection's orbits and latitude range).

### Catalog view
- deck.gl `ScatterplotLayer` of all rows of `frames.arrow` (loaded once,
  typed arrays straight from Arrow), positions computed per view mode:
  cylindrical (x = lon east 0-360, y = lat) or polar N/S
  (x = rho cos lon, y = rho sin lon with rho = 90 - |lat|), toggled in
  the view toolbar; `OrthographicView` with a graticule `PathLayer`
  (10-degree lines) and, in polar mode, latitude circles.
- Filters in the view toolbar (same set as the contract's summary
  filters) applied client-side to the typed arrays; the summary
  charts (frames per latitude band, per orbit, per month) are Plotly
  bars fed by `/api/catalog/summary` with the same filters (server
  side, so the numbers match the API).
- Hover: tooltip with product id, time, pixel km, emission, orbit,
  sequence; click: a detail card (GET `/api/catalog/frame/{id}`) with
  a "add to selection" button. Box and lasso selection tools (deck.gl
  picking with `pickObjects`, or a polygon test in the typed arrays)
  adding to the tray.
- A paginated table of the filtered rows (virtualised, no external
  table library required: render 200 rows with a page control) with
  checkboxes and a CSV download of the filtered set (client-side blob).
- Colour of points by orbit, year, pixel size, or emission (legend).

### Poles view
- Stack list from `/api/stacks` (region, band, level, n_time, size,
  movie badge); pick one -> load `/meta`.
- Viewer: deck.gl `OrthographicView` with a `BitmapLayer` showing the
  current frame PNG (grayscale in R, alpha for validity) through a
  custom colour-map shader or, simpler, by drawing the PNG into a
  canvas and mapping through a 256-entry LUT before handing it to the
  layer (instant colour map change; LUTs for gray, viridis, magma,
  inferno, cividis generated in code). Bounds from `X-Bounds`. Aspect
  locked; zoom and pan; a `PathLayer` graticule from `meta.graticule`
  toggled by a checkbox; emission overlay (second BitmapLayer, alpha
  slider) from the emission PNG.
- Controls: time slider with play/pause and speed, stretch sliders
  (vmin/vmax initialised from `meta.stretch`; changing them refetches
  the PNG, debounced), colour map, frame metadata panel from
  `meta.per_time[t]`.
- Movie: if `has_movie`, a native `<video controls>` element pointing
  at `/api/stacks/{id}/movie` beside the viewer; "Render movie" posts
  the job and, when the job is done (poll `/api/jobs/{id}` every 2 s),
  reloads the video element. "Export triples" posts the export job and
  shows the result path.
- Prefetch the next two frames' PNGs while playing.

### Strips view
- Table of `strips.arrow` rows with filters (latitude band, epoch
  range, resolution class, valid fraction, dayside, band) and a small
  deck.gl map of strip centres (cylindrical) coloured by year with hover
  and click; clicking a row or a point loads the strip.
- Viewer as in Poles (BitmapLayer + LUT, graticule, local-time
  contours from `meta.local_time_contours`, hover readout of km
  coordinates; latitude/longitude readout via bilinear lookup is
  optional).
- Statistics panel: three Plotly plots from `/api/strips/{id}/stats`:
  isotropic spectrum (log-log, secondary annotation of wavelength in
  km), 1-D spectra along x and y, structure functions S2 (log-log) and
  S3 (linear, signed). "Download stats (JSON)".

## Behaviour rules
- Every remote call shows a loading state and an error toast; the app
  never freezes on a failed request.
- State in one zustand store: config, catalog table, filters,
  working selection, saved selections, current stack/frame/strip,
  jobs. Persist filters and the working selection to `localStorage`.
- No data larger than the catalog Arrow table is held in memory; frame
  PNGs are cached in a small LRU (20 entries).
- Accessibility basics: all controls are labelled; keyboard left/right
  step the time slider.

## Tests
- vitest: filter functions on a synthetic Arrow table; the projection
  functions (cylindrical, polar N/S) including the antimeridian;
  latitude-band binning; LUT generation (256 entries, endpoints);
  selection store operations (add, remove, replace, save round trip
  with a mocked fetch).
- Playwright e2e (`frontend/e2e/`): against a running backend at a
  base URL from `E2E_BASE_URL` (default `http://127.0.0.1:5006`).
  Tests: the catalog renders and the point count in a debug element
  `#debug-state` (a hidden `<pre>` with JSON of `{n_points, n_filtered,
  selection_n, view, stack_id, t, cmap}` updated on every state change)
  is >= 40,000; changing a filter reduces `n_filtered`; hovering the
  centre of the canvas after zooming to a dense area shows a tooltip
  element (`.tooltip`) with a product id; box selection increases
  `selection_n`; opening the sequence stack sets `stack_id` and the
  first frame image loads (an `<img>` or canvas `data-loaded="true"`);
  changing the colour map changes `cmap` and a sampled canvas pixel
  colour; the video element has `readyState >= 1` after load; a strip
  stats plot renders (Plotly `.js-plotly-plot` present). Build the
  bundle before e2e (`npm run build`), and start the backend yourself
  (`uv run jiram-catalog gui --port <free> --no-browser`) only if it
  exists in `src/jiram_catalog/api/`; if the backend is not there yet
  when you finish, run the unit tests and the build, mark the e2e as
  "not run", and say so.

## Validation that defines done
```
cd frontend && npm ci && npm run typecheck && npm test && npm run build
ls -la src/jiram_catalog/webapp/dist/index.html
cd frontend && npx playwright test        # when the backend exists
```
The READ-ONLY gate `tests/test_gate_frontend.py` (Python, run by the
coordinator) starts the backend, runs the Playwright suite as a
subprocess, and asserts it passes; it also checks the bundle is under
8 MB and that `dist/index.html` references hashed assets.
